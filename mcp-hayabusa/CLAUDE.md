## Purpose

An MCP (Model Context Protocol) server that wraps [Hayabusa](https://github.com/Yamato-Security/hayabusa) — the Windows event log (EVTX) analysis and threat-hunting CLI tool — so that MCP clients (e.g. Claude Code) can run EVTX scans and consume structured results.

In addition to the Hayabusa scanning functionality, this project is also an MCP server providing a
**detection engineering knowledge base**: Sigma detection rules and ATT&CK technique mappings
exposed as browsable resources and queryable tools, alongside the EVTX scanning capability.

## Goals

- Expose a `scan_evtx` MCP tool that runs the Hayabusa CLI against one or more EVTX files, with `min_severity`, `rule_filter`, `output_format` (summary/full), and `max_results` parameters.
- Expose a `get_hayabusa_rules` MCP tool that lists available detection rules (optionally filtered by keyword), so a client can see what rules exist before scanning.
- Return Hayabusa's findings as structured JSON (not raw CLI text output).
- Handle errors gracefully — e.g. missing/invalid EVTX files, Hayabusa not installed or not on PATH, non-zero exit codes, malformed output — and surface them as clear MCP tool errors rather than crashing the server.
- Expose Sigma rules as browsable MCP resources (`detection://rules`, `detection://rules/{rule_name}`).
- Expose ATT&CK technique-to-rule mappings (`detection://rules/by-technique/{technique_id}`), derived by parsing `attack.tXXXX` tags out of our Sigma rules — no separate mapping file to keep in sync.
- Allow Claude to query detection coverage per technique via `detection://attack/techniques/{technique_id}`, which returns the ATT&CK technique's name/description, which of our rules detect it, and a `covered` / `partial` / `gap` assessment (gap = no matching rule; partial = matching rule(s) below medium severity; covered = at least one medium+ severity rule).
- Combine the knowledge base with Hayabusa scanning (from Module 3) so results can be cross-referenced against ATT&CK coverage.
- Expose an `analyze_coverage` MCP tool that aggregates this covered/partial/gap assessment across an entire ATT&CK tactic (or a single technique), returning a summary count plus a list of gap techniques, so coverage can be reviewed at the tactic level instead of one technique at a time.
- Expose a `suggest_rule` MCP tool that, given a technique ID, reports existing coverage and — if it's a gap — searches Hayabusa's bundled rule set for a rule already tagged with that technique to recommend promoting, or flags it as needing a rule written from scratch. Optionally (`create_template=True`) writes a starter Sigma rule into `rules/<category>/`, seeded from the candidate rule's actual detection logic when one exists.

## Structure

- `rules/` — our curated Sigma detection rules (YAML), organized by Sigma category subfolder (`process_creation/`, `powershell/`, `registry/`, `process_access/`, `create_remote_thread/`). Separate from Hayabusa's own bundled rule set under `hayabusa/rules/`.
- `attack/techniques.json` — trimmed MITRE ATT&CK Enterprise technique index (id → name/description/tactics), generated by `scripts/download_attack_data.py` from the full ~50MB STIX bundle so the server never has to load that directly.
- `server.py` — MCP server exposing both resources (Sigma rules, ATT&CK technique coverage) and tools (Hayabusa scanning, rule listing).
- `scripts/download_attack_data.py` — one-time fetch of MITRE ATT&CK data (mirrors `scripts/download_hayabusa.py`'s pattern for the Hayabusa binary).

## Stack

- Python, using the `mcp` library (MCP Python SDK) to implement the server.
- Hayabusa CLI, expected to be installed locally and invoked as a subprocess (not reimplemented in Python).

## Setup

- Install dependencies: `pip install -r requirements.txt`
- `requirements.txt` pulls in `mcp` and `pyyaml`. Invoking Hayabusa is done via the stdlib `subprocess` module, and its JSONL output is parsed with the stdlib `json` module — no extra HTTP, CSV, or dataframe libraries needed there. `pyyaml` is used to read rule metadata (title, level, tags, etc.) out of YAML rule files, both Hayabusa's bundled set under `./hayabusa/rules` and our own Sigma rules under `./rules`. Add a dependency only when a concrete need for it shows up.
- Run `python scripts/download_attack_data.py` once (or whenever the ATT&CK data should be refreshed) to populate `attack/techniques.json`; the `detection://attack/techniques/{technique_id}` resource reads from that file and will error with an actionable message if it's missing.

## Architecture notes

- The server is a thin wrapper: it shells out to the Hayabusa binary rather than parsing EVTX files itself. Hayabusa does the log parsing and rule matching; this server's job is invocation, output translation (to JSON), filtering, and error handling.
- Since Hayabusa is an external local dependency, prefer failing fast with an actionable error (e.g. "hayabusa not found on PATH") over silently degrading.
- Severity filtering can likely be done via Hayabusa's own CLI flags where available, falling back to post-filtering the JSON output otherwise — check current Hayabusa CLI capabilities before choosing an approach.
- ATT&CK technique IDs are extracted from Sigma rule tags (`attack.t1003.001` → `T1003.001`) via regex, not stored redundantly — the rule YAML files are the single source of truth for which techniques we detect.
- The full MITRE ATT&CK STIX bundle is ~50MB; `scripts/download_attack_data.py` downloads it once and extracts only technique id/name/description/tactics into a much smaller `attack/techniques.json`, which is what `server.py` actually loads at runtime (cached in memory after first read, same pattern as the Sigma/Hayabusa rule caches).
- Coverage assessment (`covered`/`partial`/`gap`) is computed on the fly from matching rules' `level` field against `COVERED_MIN_LEVEL` in `server.py` — not a stored classification, so it stays consistent with the rules as they change.
- `analyze_coverage` and `suggest_rule` are layered on the same helpers backing the `detection://...` resources (`_load_sigma_rules`, `_get_sigma_rules_by_technique`, `_assess_coverage`) rather than duplicating coverage logic.
- `suggest_rule`'s Hayabusa-candidate ranking sorts by (not-deprecated, severity level, stable-status) — deprioritizing `deprecated`-status rules ahead of severity, so a maintained rule doesn't lose to a stale one at the same level.
- Generated rule templates (`suggest_rule` with `create_template=True`) copy their `logsource`/`detection` blocks directly from the seeding Hayabusa rule's own YAML rather than guessing from its file path, and are written under `rules/<category>/` where `<category>` is derived from that real logsource — this can create category subfolders beyond the original five (e.g. `rules/security/`) when a gap's telemetry doesn't fit them. Writing a template invalidates the in-memory Sigma rule cache so coverage queries immediately reflect it.
